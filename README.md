# 🎟 Промо-акция «Чек на удачу»

Решение тестового задания: небольшое веб-приложение, в котором **покупатель регистрирует чек**, а **модератор проверяет его** в админке и меняет статус.

**Стек:** Python 3.12, Django 5.2, PostgreSQL 16, Docker, Django REST Framework. Фронтенд — шаблоны Django + чистый JavaScript (без фреймворков).

---

## Быстрый старт (Docker)

```bash
cp .env.example .env     # при необходимости поменяйте даты акции и секреты
docker compose up --build
```

После старта:

- сайт: <http://localhost:8000>
- админка: <http://localhost:8000/admin/> (логин `admin`, пароль `admin12345` — берутся из `.env`)
- При старте автоматически выполняются миграции, сборка статики и создание суперпользователя (если не существует).

**Период акции** задаётся в `.env`: `PROMO_START_DATE`, `PROMO_END_DATE`, `PROMO_TIMEZONE`. На страницах период выводится из настроек.

> ⚠️ Пароль суперпользователя в примере — только для локальной разработки, в реальном репозитории смените значения в `.env`.

### Локальная разработка без Docker

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows; на Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt

copy .env.example .env          # в .env поставьте DB_ENGINE=sqlite для запуска без Postgres
python manage.py migrate
python manage.py runserver
```

Тесты:

```bash
python manage.py test receipts
```

## Возможности

**Пользователь:**

- регистрация и вход (стандартный `django.contrib.auth`), при регистрации обязателен корректный и уникальный e-mail;
- регистрация чека: **ФН → Номер чека (ФД) → ФП → Дата покупки → Сумма** (порядок полей — по макету);
- быстрый путь: раздел «У меня есть фото или QR-код чека» — при загрузке фото QR-код распознаётся прямо в браузере (jsQR) и реквизиты заполняются автоматически; можно вставить и текстовую строку из QR-кода;
- серверная валидация:
  - дата покупки — внутри периода акции из `.env` (границы включительно), «чек из будущего» отклоняется;
  - сумма — не меньше 1000 ₽;
  - связка **ФН + ФД + ФП** уникальна: дубликат не принимается с понятным сообщением (и на уровне БД — частичный уникальный индекс);
  -   новый чек всегда получает статус «На проверке»;
  - личный кабинет «История чеков»: бейдж количества, таблица (дата покупки, статус, сумма, дата регистрации, причина отказа), нумерованная пагинация по 10, инфо-баннер о сроках проверки;
  - страница **«Правила»** (`/rules/`) — условия участия, порядок розыгрыша и описание всех статусов чека;
  - после окончания акции запускается **автоматический розыгрыш**: принятые чеки получают статусы «Выиграл» / «Не повезло» (победителей определяет `PROMO_WINNERS_COUNT` из `.env`, один приз на участника); победитель при входе видит поздравительный **попап** «Вы победитель, поздравляем!» (показывается один раз на браузер), а у всех чеков в истории обновляются статусы;
  - клиентская валидация на чистом JS: ошибки подсвечиваются рядом с полями до отправки, форма уходит через `fetch`, ответ сервера показывается на странице (успех и ошибка оформлены по-разному);
- адаптив под 375px: шапка складывается, таблица превращается в карточки, горизонтального скролла нет.

**Модератор (админка):**

- список чеков с фильтрами и поиском, смена статуса;
- **массовые действия над выбранными чеками:** «Принять выбранные» одним кликом и «Отклонить выбранные (с причиной)» — с промежуточной страницей, где модератор указывает причину отказа;
- при статусе «Отклонён» причина обязательна; при возврате в другой статус причина очищается;
- потоковая выгрузка принятых чеков в CSV (BOM для Excel) — `StreamingHttpResponse` отдаёт файл чанками, выгрузка даже большого списка не занимает память сервера.

**API (DRF):**

- `GET /api/receipts/` — чеки текущего пользователя в JSON (пагинация по 10). Всегда фильтруется по `request.user`; посторонние параметры запроса (`user_id`, `id`, …) игнорируются и не могут раскрыть чужие чеки.

## Спорные места и принятые решения

Подробно в [research/plan.md](research/plan.md). Коротко:

1. **Границы акции и часовые пояса.** Даты в `.env` — календарные, период = от 00:00 начала до конца последнего дня **в часовом поясе акции** (`PROMO_TIMEZONE`). Введённое пользователем время покупки трактуется как местное время акции и хранится в UTC. Часовой пояс покупателя на границы не влияет: у акции одна граница, иначе один и тот же чек был бы то в акции, то вне её.
2. **Повторная подача отклонённого чека — разрешена.** Частичный уникальный индекс `(fn, fd, fp)` действует только для статусов «На проверке» и «Принят». Отклонённый чек можно зарегистрировать заново (например, исправить ошибку), а «живые» дубликаты блокируются на уровне БД даже при одновременных запросах — пользователь получает понятное сообщение вместо 500.
3. **«Чек из будущего» отклоняется** с допуском 5 минут (расхождение часов устройства).
4. **Причина отказа** обязательна только при статусе «Отклонён» и очищается при смене статуса.
5. **Статусы — пять** («На проверке» / «Принят» / «Отклонён» / «Выиграл» / «Не повезло»). Первые три — по тексту ТЗ; «Выиграл» и «Не повезло» появляются после автоматического розыгрыша по окончании акции. Частичный уникальный индекс ФН+ФД+ФП действует для всех «живых» статусов (на проверке, принят, выиграл, не повезло) — повторная подача того же чека после розыгрыша невозможна, а отклонённый чек можно подать заново. Цвета статусов: жёлтый / зелёный / красный / фиолетовый / серый.
6. **Розыгрыш.** Команда `draw_winners` запускается автоматически при старте контейнера после даты окончания акции (`PROMO_END_DATE` в поясе `PROMO_TIMEZONE`) и выбирает `PROMO_WINNERS_COUNT` победителей случайно из принятых чеков. Один приз на участника (берётся последний принятый чек). Команда идемпотентна: повторный запуск ничего не меняет, `--force` позволяет провести заново.
7. **API:** любые query-параметры игнорируются, выборка жёстко `filter(user=request.user)`; тест доказывает, что чужие чеки не утекают даже с параметрами, указывающими на них.

Полный журнал разработки — какие проблемы возникали и как их решали (включая историю с CSV) — ведётся в [research/dev-notes.md](research/dev-notes.md).

## Работа с ИИ

Использовал Claude Code в режимах Architect (планирование) и Code (реализация).

- **Где ИИ помог сильнее всего:** спроектировал каркас приложения и модульную структуру, сгенерировал большую часть кода (модель, формы, API, шаблоны), быстро разложил бэкенд по слоям и подготовил Docker-инфраструктуру; помог найти причины падающих тестов.
- **Что ИИ выдал неправильно и как это заметили:**
  - `django.utils.timezone.utc` удалён в Django 5.2 — поймали на первом же прогоне тестов;
  - перепутал имя функции (`promo_period_display` vs `campaign_period_display`) — поймали по `ImportError`;
  - главное — ИИ не учёл, что Django-форма сама интерпретирует наивный ввод времени как текущий часовой пояс (UTC), из-за чего границы акции «съезжали» на 7 часов. Это выявили только тесты с фиксацией времени, и обработку времени пришлось переписать вручную: извлекать «настенные часы» ввода и трактовать их как время акции;
  - потоковый CSV: генератор вызывал `writer.writerow(...)`, но не отдавал результат через `yield`, поэтому файл содержал только BOM. Заметили по тесту, который собирал `b"".join(response.streaming_content)` — диагноз подтвердился shell-проверкой `list(_csv_rows(qs)) == ['\ufeff']`; решение — буфер `io.StringIO` с переиспользованием;
  - тесты «зелёные на SQLite, красные на PostgreSQL»: тестовый хелпер генерировал ФН длиной 18 цифр, а поле — `varchar(16)`; SQLite длину не проверяет, Postgres падает с `StringDataRightTruncation` — поймали только при прогоне в Docker;
  - мокание `timezone.now` ломало сессии тестового клиента (302 вместо 200) — пришлось переносить `force_login` внутрь `with patch_now():`.
- **Что бы я переписал, будь больше времени:** разбить JS на ES-модули с собственными тестами (валидация, QR-парсер), вынести статусы чеков в отдельный справочник, добавить CSV-импорт из админки и полноценный лог действий модератора; розыгрыш — в фоновую задачу (сейчас он срабатывает при старте контейнера); сразу покрыть стриминговый CSV тестом на «непустоту», чтобы не поймать баг с `yield` на живом сайте.
