# Журнал разработки: проблемы, решения, улучшения

Хронология всех значимых проблем, встреченных при разработке промо-акции «Чек на удачу»,
как их решали и что можно было бы сделать лучше. Дополняет [README](../README.md).

---

## Итерация 1 — MVP (регистрация чека, кабинет, админка, API)

| # | Проблема | Причина | Решение |
|---|----------|---------|---------|
| 1 | `NameError: Status` в `Meta` модели (constraint, ordering) | Ссылались на `Status` до определения класса | Вынести `Status` в `class Status(models.TextChoices)` внутри модели до `Meta` |
| 2 | `AttributeError: module 'django.utils.timezone' has no attribute 'utc'` | `django.utils.timezone.utc` удалён в Django 5.2 | Использовать `datetime.timezone.utc` (импорт `timezone as dt_timezone`) |
| 3 | Границы акции «съезжали» на 7 часов (пояс акции Asia/Novosibirsk) | Django-форма сама трактует наивный ввод времени как *текущий* пояс (UTC) | В `clean_purchased_at` извлекать «настенные часы» из ввода, проверять границы по ним и делать aware-время в `PROMO_TIMEZONE` |
| 4 | «Чек из будущего» проходил валидацию | Не было ограничений на поле даты | `min`/`max` на поле + клиентская проверка с допуском 5 минут (расхождение часов устройства) |
| 5 | Пустые красные блоки ошибок занимали место в форме | `p.field-error` рендерился даже без текста | CSS: `.field-error:empty { display: none; }` |
| 6 | Дубликат ФН+ФД+ФП при одновременных запросах давал 500 | Race condition, проверка только на уровне приложения | Частичный уникальный индекс `UniqueConstraint(condition=Q(status__in=[...]))` + понятное сообщение |

## Итерация 2 — обратная связь №1 (email, QR, ошибки, границы)

| # | Проблема | Причина | Решение |
|---|----------|---------|---------|
| 7 | Регистрация без e-mail или с невалидным/повторным e-mail | Стандартный `UserCreationForm` не требовал email | Кастомная форма: обязательный, корректный и уникальный e-mail (`clean_email`) + тесты |
| 8 | QR-код из фото чека не распознавался | Нужна JS-библиотека, а CDN ненадёжен | jsQR подключён локально (vendored: `receipts/static/receipts/js/vendor/jsqr.min.js`); распознавание прямо в браузере |
| 9 | Поле «строка из QR» не автозаполняло форму | Вставка применялась в `clean()` — уже после валидации полей | Автозаполнение перенесено в `__init__` формы через mutable `QueryDict` (`_apply_qr_autofill`) — до валидации |
| 10 | Сервер не разбирал строку из QR | Парсер был только на клиенте | Парсер `t=...&s=...&fn=...&i=...&fp=...` продублирован на сервере (`receipts/qr.py`) |

## Итерация 3 — обратная связь №2 (админка, мобильная вёрстка, индексы)

| # | Проблема | Причина | Решение |
|---|----------|---------|---------|
| 11 | «Отклонить выбранные» без причины | Одиночное действие на каждый чек | Массовые действия: «Принять выбранные» одним кликом и «Отклонить выбранные (с причиной)» с промежуточной страницей (`TemplateResponse`) |
| 12 | 403 при POST на промежуточную страницу админки | Нет CSRF-токена в проверочных скриптах | CSRF обязателен на POST админки; проверочные скрипты стали передавать токен |
| 13 | Массовые действия в проверочных скриптах падали с 500 | `urlencode` без `doseq=True` превращал список id в строку `['5']` | `urllib.parse.urlencode(data, doseq=True)` для повторяющихся ключей `_selected_action` |
| 14 | Горизонтальный скролл на 375px | Таблица не адаптировалась | Мобильные отступы, таблица превращается в карточки, шапка складывается |
| 15 | Медленная выборка «все чеки пользователя, отсортированные по дате» | Не было подходящего индекса | `models.Index(fields=["user", "-created_at"])` + второй ключ `-id` в `ordering` для детерминированного порядка |

## Итерация 4 — обратная связь №3 (CSV, правила, розыгрыш)

| # | Проблема | Причина | Решение |
|---|----------|---------|---------|
| 16 | **CSV-выгрузка даёт 500 (главная проблема)** | Два слоя: (а) баги моих проверочных скриптов (см. №13) имитировали 500; (б) реальный баг — см. №17 | Полный HTTP-сценарий (логин + POST действия) вместо «дырявых» скриптов |
| 17 | CSV отдавал только BOM, без заголовка и строк | В генераторе результат `writer.writerow(...)` не отдавался через `yield` — потоковый ответ получал лишь первую строку | `io.StringIO` с переиспользованием буфера (`seek(0); truncate(0)`) на каждую строку + `StreamingHttpResponse`; запись больше не зависит от возвращаемого значения `writerow` |
| 18 | Тесты падали на PostgreSQL: `value too long for character varying(16)` (на SQLite проходили) | SQLite не проверяет длину `varchar`, Postgres проверяет; тестовый хелпер генерировал ФН из 18 цифр | ФН в тестах — ровно 16 цифр (с `%`-форматом и модулем) |
| 19 | Розыгрыш мог выбрать несколько призов одному участнику или «перезапуститься» | Не было ограничений | Команда `draw_winners`: один приз на участника (последний принятый чек), идемпотентность (guard по статусам won/lost), `--force` для принудительного перезапуска, количество из `PROMO_WINNERS_COUNT` (`.env`) |
| 20 | Попап «Вы победитель» надоедал бы при каждом входе | Нет памяти о показе | localStorage-флаг `lucky_receipt_win_popup_dismissed` — показ один раз на браузер |
| 21 | Розыгрыш должен запускаться автоматически | Нет планировщика | Вызов `draw_winners` в `entrypoint.sh` перед стартом gunicorn (идемпотентная команда безопасна при каждом старте) |

## Инфраструктурные ограничения окружения

| # | Проблема | Решение |
|---|----------|---------|
| 22 | Windows `cmd`: нет `head`/`grep`, многострочный `python -c "..."` ломается (SyntaxError) | Проверочные скрипты как полноценные `.py`-файлы, перенос в контейнер через `docker cp` |
| 23 | `entrypoint.sh` портился CRLF на Windows | `.gitattributes`: `*.sh text eol=lf` |
| 24 | Локальный Python без DRF — тесты не запускались вне контейнера | Прогон тестов внутри контейнера: `docker compose exec web python manage.py test receipts` |
| 25 | Мокание `timezone.now` ломало сессии тестового клиента (302 вместо 200) | `force_login` и все запросы выполнять внутри `with patch_now():` |

## Что можно было бы улучшить дальше

- **Публичный «живой» розыгрыш** с фиксацией результатов в отдельной таблице (история розыгрышей, номер тиража) — сейчас итог только в статусах чеков.
- **E-mail-уведомления победителям** о результате розыгрыша.
- **Rate limiting** на отправку чеков против спама (сейчас только валидация и уникальность).
- **Фоновая задача** (Celery / task queue) вместо запуска `draw_winners` в `entrypoint` — сейчас розыгрыш срабатывает при рестарте контейнера, а не точно в момент окончания акции.
- **ESM-модули** для JS + unit-тесты фронтенда (валидация, QR-парсер, логика попапа).
- **CSV-импорт** из админки для массового ввода чеков.
- **Аудит действий модератора**: вывести `django.contrib.admin.LogEntry` в отдельную страницу.
- **Фильтр по сумме** и экспорт с фильтрами в админке чеков.
- **Справочник статусов** (FK-модель) вместо `TextChoices` — проще добавлять новые состояния без миграций индекса.
- **Разделение настроек dev/prod**, `django-compressor` или сборка CSS/JS.
- **Тест на поведение `csv.writer` + `Echo`** сразу после перехода на стриминг — замечание №17 нашлось бы мгновенно.
- **Демо-данные / фикстуры** (`manage.py loaddata`) для мгновенного старта.
